PolinRider Campaign Spreads Across npm, Packagist, Go Modules, and Chrome Extensions

Socket reports an active North Korea-linked supply-chain campaign using compromised repositories and hidden JavaScript loaders to target developer environments across multiple ecosystems.

Socket

What happened

Socket’s research describes PolinRider as an ongoing developer-focused supply-chain campaign tied to the Contagious Interview / Famous Chollima activity cluster. The reported activity spans npm, Packagist, Go modules, and at least one Chrome extension, with 162 malicious release artifacts across 108 packages or extensions. Attackers appear to compromise legitimate maintainer accounts or repositories, insert obfuscated JavaScript loaders, and in some cases publish infected package versions downstream. The snippets do not include a full package/version list, so exposure assessment depends on Socket’s live tracker or internal package telemetry.

Key findings

  • Socket identified 162 malicious release artifacts across 108 packages and extensions.
  • The affected scope reportedly includes npm packages, 10 Packagist packages, compromise traces in 80 Go modules, and one Chrome extension.
  • Attackers hide JavaScript loader code using techniques such as long whitespace padding, fake font files, and developer-tooling execution paths including VS Code task files.
  • The campaign reportedly uses Git history manipulation, including force pushes and backdated commits, making normal repository browsing insufficient for verification.
  • Observed loaders contact public blockchain/RPC infrastructure, including TRON, Aptos, and BNB Smart Chain services, to retrieve encrypted follow-on payload material.
  • Socket says observed payloads include DEV#POPPER and OmniStealer, but the loader design could support other second-stage malware.

Affected ecosystems

npm, Packagist / PHP Composer, Go modules, Chrome extensions, GitHub-hosted source repositories and maintainer accounts, Developer workstations using affected dependencies or repository task configurations

Security analysis

This incident is notable because it combines package ecosystem abuse with repository-level compromise. Rather than relying only on typo-squatting or throwaway packages, the operators reportedly modify legitimate projects and use registry access where available to distribute infected releases. That raises the risk for teams that trust upstream repositories, auto-update dependencies, or run developer tooling automatically during install, build, or editor startup. The use of hidden one-line JavaScript, deceptive file placement, and VS Code task execution is especially relevant to AppSec teams because compromise may occur before production deployment, on developer laptops or CI workers that hold high-value credentials. The source indicates the campaign is active and that more artifacts may be found. Because the provided snippet does not enumerate all affected package names and versions, defenders should treat this as a prioritization signal rather than a complete IOC set.

Defender actions

  • Inventory recent installs and lockfile changes across npm, Composer, Go modules, and browser extensions, then compare against confirmed affected package/version indicators from Socket or other trusted feeds.
  • Do not rely only on the visible GitHub commit timeline. Review repository audit logs, release metadata, force-push events, tag changes, and anomalous synchronized commits.
  • Inspect VS Code task files, package scripts, build hooks, configuration files, and unusual assets such as font files that may contain hidden loader code.
  • If an affected version was installed or built, treat the developer environment as potentially compromised: preserve forensic evidence, isolate the host, and rebuild from a known-good baseline.
  • Rotate credentials, tokens, SSH keys, package registry tokens, cloud secrets, and cryptocurrency-related secrets from a clean machine.
  • Pin dependencies to known-good versions and verify package integrity before rebuilding. Recreate lockfiles only after malicious versions have been excluded.
  • Audit maintainer accounts for takeover paths, including stale recovery emails, expired domains, weak MFA coverage, and unnecessary registry publish permissions.
