Slopsquatting turns AI package hallucinations into dependency risk

AI coding agents can suggest plausible but nonexistent packages; attackers can register those names in public registries and use normal install paths to deliver malware.

Endor Labs

What happened

Endor Labs describes “slopsquatting,” a software supply-chain risk in which AI coding tools hallucinate dependency names that do not exist. An attacker can identify recurring hallucinated names, register them on ecosystems such as npm or PyPI, and publish packages with malicious install-time behavior. The source frames this as an emerging attack pattern rather than naming a specific active campaign or confirmed malicious package set, so defenders should treat the report as a practical dependency-risk warning with incomplete incident details.

Key findings

  • The risk differs from typosquatting: the package name may not resemble a real dependency, so similarity checks alone may not flag it.
  • LLMs can generate plausible package names without verifying registry existence, and some hallucinated names may recur across prompts, making them attractive for pre-registration.
  • Agentic development tools increase exposure when they can add or install dependencies with limited human review.
  • Malicious packages in this pattern could use install scripts to steal environment variables, source-control credentials, cloud keys, or CI/CD secrets.
  • Once accepted, a hallucinated dependency can be committed to a manifest or lockfile and propagate through build and deployment pipelines.

Affected ecosystems

npm, PyPI, AI-assisted development workflows using tools such as coding assistants or agentic IDEs, CI/CD environments that install dependencies from public registries

Security analysis

Slopsquatting is important because it exploits a trust gap in AI-assisted development rather than a traditional developer typo. A package name generated by a model can look reasonable, fit the project’s language ecosystem, and still have no legitimate history. If an attacker registers that exact name before a developer installs it, the public registry becomes the delivery channel. The highest-risk environments are those where agents can modify manifests, run package managers, or execute chained commands without review. Current evidence in the provided source does not identify specific malicious packages, victims, or registry takedowns, so teams should prioritize preventive controls and dependency-intake review rather than incident-specific blocking.

Defender actions

  • Require human review for any AI-suggested dependency before it is added to a manifest or lockfile.
  • Verify package existence, publisher, release history, download patterns, repository links, and maintenance signals before installation.
  • Block or closely review new dependencies introduced by AI-generated commits, especially packages with little history or newly created names.
  • Disable or restrict automatic dependency installation by coding agents where possible.
  • Use lockfile and software composition analysis controls to detect unexpected new packages in pull requests.
  • Limit install-script execution in CI/CD when feasible, and run dependency installation with least-privilege credentials.
  • Keep secrets out of build environments unless required; monitor for environment-variable and credential access during package install steps.
  • Create allowlists or internal mirrors for approved dependencies used in sensitive projects.
