Typosquatted Braintree NuGet package targeted payment data and merchant secrets

A malicious NuGet package named Braintree.Net impersonated the official Braintree .NET SDK and included code to skim card data and steal API credentials from applications that installed it.

Socket

What happened

Socket reported a NuGet typosquatting campaign against .NET developers integrating PayPal Braintree payments. The malicious package, Braintree.Net, used the legitimate project’s branding and repository metadata while differing from the official package ID, which is Braintree. Confirmed malicious Braintree.Net releases were published in the 3.35.8–3.36.1 range, with later versions pulling in a companion package, DependencyInjector.Core, that Socket says contained an additional token-harvesting payload. The package reportedly mirrored enough of the Braintree SDK API surface to appear functional while intercepting payment card data, Braintree merchant API keys, and host environment secrets, then sending stolen data to attacker-controlled infrastructure. Some SipNet packages were also identified as transitively affected through the malicious DependencyInjector.Core dependency.

Key findings

  • The affected package ecosystem is NuGet/.NET, with direct risk to applications handling Braintree payment flows.
  • The malicious package name Braintree.Net is a plausible variation of the legitimate NuGet package Braintree, increasing the risk of developer copy-paste or search-result mistakes.
  • Socket lists confirmed malicious versions as pkg:nuget/braintree.net@3.35.8, 3.35.9, 3.36.0, and 3.36.1.
  • Socket also lists malicious DependencyInjector.Core versions 1.0.0, 1.3.0, 1.4.0, and 1.4.1; Braintree.Net 3.36.0 and later reportedly depended on this companion package.
  • Transitive exposure was reported for sipnet versions 12.8.4 through 12.8.7 and sipnet.openai.realtime 12.8.3 through its sipnet dependency.
  • The reported command-and-control endpoint was api.348672-shakepay[.]com.
  • Download counts for Braintree.Net may overstate real exposure because Socket says many earlier placeholder versions appeared to inflate package popularity; the actual number of installs of malicious releases is uncertain from the snippet.

Affected ecosystems

NuGet, /.NET applications using Braintree payment integrations, Applications depending on Braintree.Net, DependencyInjector.Core, SipNet, or SipNet.OpenAI.Realtime versions identified by Socket

Security analysis

This is a high-impact package-confusion case because the malicious dependency sat directly in the payment path. Unlike commodity packages that only run install scripts, this package reportedly exposed a convincing Braintree-compatible API and could therefore be deployed into production before obvious functional failures appeared. That raises the value of exposure analysis beyond simple developer-workstation checks: defenders should inspect application dependency manifests, CI artifacts, container images, package caches, and deployed assemblies for the affected NuGet package IDs and versions. The transitive DependencyInjector.Core and SipNet findings also mean teams should not limit review to projects that intentionally selected Braintree.Net. The available source does not independently confirm removal status from NuGet or the full number of affected downstream applications, so organizations should base response on internal evidence of installation or execution and assume credential exposure where the package ran in environments containing payment or merchant secrets.

Defender actions

  • Search source repositories, lockfiles, project files, package caches, build logs, and SBOMs for Braintree.Net, DependencyInjector.Core, sipnet, and sipnet.openai.realtime at the versions named above.
  • Verify that Braintree integrations use the official NuGet package ID Braintree from the expected publisher rather than Braintree.Net or similarly named packages.
  • If any affected package was present in a build or runtime environment, treat Braintree merchant API keys, payment gateway credentials, and exposed environment secrets as potentially compromised and rotate them.
  • Review payment-processing logs for anomalous transaction behavior and investigate any outbound traffic to api.348672-shakepay[.]com or related infrastructure.
  • Rebuild affected applications from clean dependency graphs after removing the malicious packages; do not rely only on runtime deletion if compromised credentials may persist elsewhere.
  • Add dependency controls that flag package-name confusion, unexpected publishers, mismatched project URLs, suspicious new transitive dependencies, and payment-related libraries with unusual version schemes.
  • For regulated payment environments, coordinate incident handling with PCI/payment operations teams because the reported payload targeted live card data.
