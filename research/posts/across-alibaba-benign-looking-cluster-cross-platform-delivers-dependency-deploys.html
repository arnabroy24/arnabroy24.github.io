Discovered 2026-07-30 / 1 source

npm package cluster used dependency-chain staging to target Alibaba developers

Socket reports that multiple benign-looking npm packages worked together to install a downloader and cross-platform RAT, apparently aimed at developers with access to Alibaba’s private @ali packages.

Socket

What happened

A malicious npm campaign used unscoped packages that resembled Alibaba private package names and combined them with additional dependencies to assemble loader behavior across the install tree. Socket’s investigation began with the package `lib-mtop`, which received new versions in late March 2026 after years of inactivity. The campaign also involved packages such as `aone-kit`, `aone-kit-cli`, `aone-sandbox`, and `local-config-parser`. Individually, some packages appeared empty or plausibly functional, but together they delivered downloader functionality leading to a targeted remote access trojan. Socket says the final payload supported data theft, command execution, and lateral movement using DingTalk-related tooling. The source does not conclusively establish whether this began with maintainer account takeover or a malicious maintainer.

Key findings

  • The campaign abused npm package naming around Alibaba’s private `@ali` scope, using unscoped lookalike packages as lures.
  • Malicious behavior was split across a dependency chain, making individual packages appear less suspicious during isolated review.
  • `lib-mtop` contained straightforward downloader behavior, fetching a hardcoded remote JavaScript payload and executing it locally.
  • `local-config-parser` reportedly implemented legitimate-looking JSON rule parsing and Node.js VM-based evaluation, but its role became suspicious in the broader dependency context.
  • The likely targets were developers or environments able to resolve Alibaba private packages, suggesting a focused dependency-confusion or internal tooling impersonation angle.
  • Socket reports the campaign remained undetected for roughly three months.

Affected ecosystems

npm, Node.js development environments, Organizations using private npm scopes, especially Alibaba `@ali` packages, Developer workstations and CI systems with access to internal package registries, DingTalk-connected enterprise environments, based on reported RAT capabilities

Security analysis

This incident is notable less for a novel loader and more for the packaging strategy. By placing small pieces of behavior in separate npm modules and using packages that impersonated private Alibaba tooling, the attackers reduced the chance that any one package would immediately appear malicious. That matters for AppSec teams because many dependency review workflows still focus on direct dependencies, package popularity, or obvious install scripts. Campaigns like this require lockfile-level review, private-registry hardening, and detection logic that correlates packages published by related accounts or installed together. The targeting also appears narrower than a broad credential-harvesting npm campaign. The lure names and dependency behavior suggest the attackers wanted environments that could access Alibaba’s private package ecosystem. However, the public source does not prove exactly which organizations were compromised, whether the maintainer account was taken over, or how many installations led to RAT execution. Defenders should therefore assess exposure based on package presence and registry access rather than assuming compromise solely from the campaign description.

Defender actions

  • Search package manifests, lockfiles, artifact caches, CI logs, and npm proxy logs for `lib-mtop`, `aone-kit`, `aone-kit-cli`, `aone-sandbox`, and `local-config-parser`.
  • Treat any developer workstation or CI runner that installed the suspect dependency tree as potentially compromised; collect forensic evidence before rebuilding where possible.
  • Review npm registry configuration to ensure private scopes such as `@ali` resolve only to trusted internal registries and cannot silently fall back to the public npm registry.
  • Block or alert on unscoped packages that resemble internal scoped package names, especially in dependency trees pulled by build systems.
  • Inspect affected hosts for unexpected curl-based JavaScript downloads, Node.js execution from temporary or package directories, unknown persistence, and outbound connections to payload infrastructure identified in vendor IOCs.
  • Rotate npm tokens, source-control credentials, cloud credentials, and DingTalk or enterprise chat credentials exposed to affected developer or CI environments.
  • Add dependency review rules that analyze full dependency trees, not just top-level packages, because this campaign relied on behavior distributed across multiple modules.

Source notes
