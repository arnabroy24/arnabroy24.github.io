AsyncAPI npm Releases Compromised to Load Miasma Botnet Payloads

Four packages under the @asyncapi npm scope shipped malicious versions that execute on module load and retrieve a second-stage payload from IPFS.

Socket

What happened

Socket reports that several AsyncAPI npm packages were compromised on July 14, 2026 and published with injected JavaScript implants. The malicious releases affect @asyncapi/generator-helpers, @asyncapi/generator-components, @asyncapi/generator, and @asyncapi/specs. Unlike many npm attacks, the payload did not rely on install lifecycle scripts; it ran when the affected module was imported by Node.js, then spawned a detached process to download and execute an encrypted second stage identified as the Miasma botnet loader. Socket says the campaign targets macOS, Linux, and Windows environments.

Key findings

  • Affected versions reported by Socket are @asyncapi/generator-helpers@1.1.1, @asyncapi/generator-components@0.7.1, @asyncapi/generator@3.3.1, and @asyncapi/specs@6.11.2-alpha.1 / 6.11.2.
  • The malicious code was inserted into normal source files rather than package lifecycle hooks, increasing the chance that CI, build tools, or developer machines execute it during ordinary use.
  • The first stage launches a background node -e process and retrieves an encrypted follow-on payload from IPFS.
  • Socket links the final payload to the Miasma tasking framework.
  • npm metadata and provenance reportedly point to GitHub Actions trusted publishing for the compromised releases, but Socket noted that public unauthenticated API access did not expose the workflow run and job logs at the time of analysis.
  • The poisoned changes reportedly appeared in a GitHub commit as well as in the npm tarballs, suggesting the compromise involved the release source path rather than only registry-side tampering.

Affected ecosystems

npm, Node.js applications and tooling that import the affected AsyncAPI packages, Developer workstations and CI runners on macOS, Linux, or Windows that installed and loaded the compromised versions

Security analysis

This incident is a high-impact npm supply-chain compromise because the malicious payload was placed in code paths that can execute during normal module loading. That bypasses common controls focused only on preinstall or postinstall behavior. The use of trusted publishing and provenance also shows a practical limitation: provenance can identify how a package was built and published, but it does not prove the source or workflow was legitimate if the repository, release workflow, or commit path was compromised. Exposure assessment should therefore be usage-based, not just install-based. Teams should identify where the affected versions were present, determine whether AsyncAPI tooling ran in those environments, and treat CI systems as sensitive targets because they often hold deployment credentials. Some details remain incomplete from the available source, including the exact initial access vector and the full scope of downstream execution, so defenders should prioritize environment review over assumptions about containment.

Defender actions

  • Search package-lock.json, npm-shrinkwrap.json, pnpm-lock.yaml, yarn.lock, SBOMs, and artifact manifests for the affected package versions.
  • Do not assume safety because install scripts were disabled; assess whether the packages were imported or executed after installation.
  • Upgrade to known-clean or patched AsyncAPI releases when available, or pin to earlier unaffected versions such as the immediately preceding versions identified by Socket pending maintainer guidance.
  • Rebuild potentially affected artifacts from clean environments after dependency remediation.
  • Review CI runners and developer endpoints that used these packages for suspicious detached Node.js processes, unexpected node -e execution, IPFS retrieval activity, persistence changes, or outbound connections matching published indicators.
  • Rotate credentials exposed to affected build or developer environments, including npm, GitHub, cloud, and deployment tokens, if execution is plausible.
  • Audit GitHub Actions release workflows, trusted publishing configuration, branch protections, and recent commits for unauthorized changes.

Source notes
