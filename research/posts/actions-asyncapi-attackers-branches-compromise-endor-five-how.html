AsyncAPI npm Packages Compromised Through Release Branch and CI Abuse

Five official @asyncapi packages reportedly shipped malicious code after attackers pushed to unprotected release branches, producing npm releases through legitimate GitHub Actions workflows.

Endor Labs

What happened

Endor Labs reports that on July 14, 2026, five official AsyncAPI npm package releases were published with obfuscated malware. The compromise appears to have occurred at the GitHub branch and CI/CD layer rather than through stolen npm credentials: unsigned commits were pushed to auto-publish release branches, triggering trusted GitHub Actions publishing workflows. Because the packages were built and published by the legitimate pipeline, the resulting npm artifacts reportedly carried valid SLSA provenance despite containing malicious code.

Key findings

  • Affected releases named by the source are @asyncapi/generator 3.3.1, @asyncapi/generator-components 0.7.1, @asyncapi/generator-helpers 1.1.1, @asyncapi/specs 6.11.2, and @asyncapi/specs 6.11.2-alpha.1.
  • The malware execution path is reported to be require-time loading, not npm lifecycle scripts, so installing with --ignore-scripts would not prevent execution if the compromised package is later imported.
  • The generator-related payload reportedly retrieved a larger third-stage component from IPFS; Endor identifies the analyzed framework as Miasma and describes capabilities including command-and-control, persistence, and optional modules for credential theft and propagation.
  • The source says some Miasma capabilities were disabled in the analyzed build, and the separate @asyncapi/specs IPFS payload had not been fully decrypted or analyzed, so the full behavior and impact remain uncertain.
  • The highest-risk package is likely @asyncapi/specs because it is a core dependency used transitively by AsyncAPI tooling, including parser, CLI, and generator-related dependency trees.

Affected ecosystems

npm, GitHub Actions-based release pipelines, AsyncAPI tooling and downstream projects that depend on @asyncapi/specs, @asyncapi/generator, @asyncapi/generator-components, or @asyncapi/generator-helpers

Security analysis

This incident is a useful reminder that package provenance does not eliminate the need to secure the release process that feeds the build. In this case, the attacker reportedly did not need to compromise npm accounts; they used write access to branches that the project’s CI trusted for publishing. That means downstream consumers could see an official package, from the expected namespace, published by the expected automation, with provenance metadata, while still receiving malicious code. AppSec teams should prioritize transitive exposure to @asyncapi/specs because of its reported download volume and central role in AsyncAPI tooling. The practical investigation question is not only whether a malicious version was installed, but whether it was loaded at runtime in a developer tool, test job, generator run, or CI workflow.

Defender actions

  • Search package-lock.json, npm-shrinkwrap.json, pnpm-lock.yaml, yarn.lock, SBOMs, artifact manifests, and CI logs for the affected versions.
  • Treat any developer workstation, CI runner, or build container that installed and executed these packages as potentially exposed, especially if application code or tooling imported @asyncapi/specs or @asyncapi/generator.
  • Do not rely on npm install --ignore-scripts as a compensating control for this incident; assess whether the compromised package was required or executed after installation.
  • Rebuild affected environments from trusted images, rotate credentials available to exposed developer or CI contexts, and review outbound network activity for IPFS retrievals or unusual command-and-control behavior around July 14, 2026.
  • Pin to known-good versions after maintainer remediation, refresh lockfiles, and block the identified malicious versions in internal package proxies or dependency policy tooling.
  • For maintainers, protect release branches, require signed commits or enforced reviews for publish-triggering branches, restrict who can push to release refs, and treat provenance attestations as build-origin evidence rather than malware-free guarantees.

Source notes

  • Primary source: Endor Labs, “How Unprotected Release Branches Let Attackers Compromise AsyncAPI,” published July 14, 2026.
  • Download figures in the source are for all versions during the measured periods, not confirmed installs of the malicious releases.
  • Attribution is unknown based on the provided source, and analysis of the @asyncapi/specs third-stage payload was incomplete in the snippet.
