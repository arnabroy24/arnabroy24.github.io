Dependency Confusion Remains a Build-Time Supply-Chain Risk

A recent Endor Labs write-up revisits how public registry packages can override private dependencies, with historical examples showing secret theft and code execution in CI environments.

Endor Labs

What happened

The source describes dependency confusion as a software supply-chain attack in which an adversary publishes a public package using the same name as an organization’s private dependency. If a build is configured to search both private and public registries and resolves to the highest available version, the malicious public package may be installed and executed. The article also groups related package ecosystem abuse patterns, including typosquatting, combosquatting, package poisoning, and maintainer account hijacking. This appears to be an analysis of an established attack class rather than disclosure of a new active campaign; the source does not provide fresh indicators, newly affected organizations, or a current malicious package list.

Key findings

  • Dependency confusion exploits package resolution behavior and registry configuration rather than a conventional software bug.
  • Exposure depends on whether internal package names are discoverable and whether builds can fall back to public registries for those names.
  • Install-time scripts are a major execution path: once a malicious dependency is selected, it may run during preinstall or postinstall steps and attempt to collect secrets, environment variables, SSH keys, or cloud credentials.
  • The source cites Alex Birsan’s 2021 proof-of-concept campaign and the 2022 PyTorch nightly dependency incident involving a malicious PyPI package named torchtriton.
  • Related risks include typosquatted or combosquatted packages and compromise of legitimate maintainer accounts, but the source does not identify a new ongoing campaign.

Affected ecosystems

Private package registries used alongside public registries, JavaScript/npm-style projects, especially where package names or package.json files leak publicly, Python/PyPI projects, as illustrated by the PyTorch nightly torchtriton incident, CI/CD systems that install dependencies with access to secrets, tokens, SSH keys, or cloud metadata

Security analysis

The practical risk is highest where internal package names are exposed through public repositories, build logs, documentation, client-side JavaScript, or error output, and where dependency managers are allowed to query public and private registries without strict source pinning. In those conditions, an attacker does not need to compromise a maintainer account; publishing a convincing public package with a preferred version may be enough to gain execution inside a developer workstation or CI runner. The more damaging outcomes come from the build environment itself: CI jobs often hold credentials, signing material, deployment tokens, and network access that exceed what application runtime dependencies should ever receive. Defenders should treat dependency resolution as part of the trusted build boundary, not as a passive download step. The source is useful as a risk refresher, but it does not establish a new wave of attacks or provide current malicious package indicators, so teams should use it to validate controls rather than hunt for a specific campaign.

Defender actions

  • Inventory private package names and check whether identical names exist in public registries, especially with higher version numbers.
  • Configure package managers so private scopes and internal package names resolve only from trusted internal registries; avoid public fallback for private dependencies.
  • Use lockfiles, pinned versions, and reproducible build controls so unexpected registry resolution changes are detected before deployment.
  • Reserve or defensively register critical internal package names in public registries where appropriate and allowed by policy.
  • Restrict install-time scripts in CI where feasible, and run dependency installation with least-privilege credentials.
  • Remove long-lived secrets from build environments, segment CI permissions, and monitor dependency install jobs for outbound network calls or unexpected DNS/HTTP activity.
  • Add dependency review checks for typo-like names, unofficial companion packages, and newly introduced transitive dependencies.
