Compromised Injective npm SDK release targeted wallet secrets

A malicious @injectivelabs/sdk-ts 1.20.21 release and related scoped packages reportedly hooked normal wallet key-derivation paths to exfiltrate private keys and mnemonics.

Socket

What happened

Socket reported that npm package @injectivelabs/sdk-ts version 1.20.21 was compromised and modified to steal Injective wallet private keys and mnemonic phrases under the cover of fake telemetry. The malicious behavior was not described as an install-time payload; it was triggered when applications used normal SDK functionality such as creating private keys from mnemonics or hex values. The same 1.20.21 version was also published across multiple @injectivelabs scoped packages that pinned the compromised SDK version, creating transitive exposure for projects that did not depend on @injectivelabs/sdk-ts directly.

Key findings

  • The affected ecosystem is npm, specifically the Injective Labs TypeScript SDK package family.
  • The primary malicious package identified is @injectivelabs/sdk-ts@1.20.21.
  • Socket lists 17 additional @injectivelabs packages at version 1.20.21 that directly or transitively depended on the compromised SDK version, including wallet, network, utility, and strategy packages.
  • The malicious code reportedly hooked key-generation or key-import workflows, including mnemonic- and hex-based private key creation, making exposure dependent on runtime use as well as installation.
  • The source states the malicious changes were introduced through an established contributor account, but the exact account compromise details are not fully established from the available snippet.
  • A clean version was reportedly published shortly after the malicious release, and the npm version was deprecated, but Socket noted that some release artifacts still existed on GitHub at the time of writing.

Affected ecosystems

npm, @injectivelabs/sdk-ts, @injectivelabs scoped npm packages, Applications handling Injective wallet creation, import, signing, or private-key workflows

Security analysis

This incident is a high-impact supply-chain compromise because the payload targeted wallet material at the point where developers and users would legitimately handle it. The lack of an install-time trigger may have reduced obvious detection signals: a project could install cleanly while still leaking secrets only when wallet functions were exercised. The transitive package releases also broaden the blast radius beyond teams that knowingly imported @injectivelabs/sdk-ts. For AppSec teams, exposure assessment should therefore combine dependency inventory with runtime behavior: identify whether affected builds were deployed, whether wallet-generation/import paths were used, and whether any real mnemonics or private keys passed through those paths. Because the source snippet does not provide complete exfiltration infrastructure details, responders should assume compromise of handled wallet secrets rather than wait for perfect network indicators.

Defender actions

  • Search package-lock.json, yarn.lock, pnpm-lock.yaml, SBOMs, artifact repositories, and container images for @injectivelabs/sdk-ts@1.20.21 and any @injectivelabs/* package pinned to 1.20.21.
  • Upgrade to a known-clean Injective SDK release and rebuild applications from clean dependency caches; do not rely only on package deprecation status.
  • Treat any wallet private key or mnemonic processed by affected runtime code as potentially compromised. Move funds to newly generated wallets and rotate any secrets derived from exposed mnemonics.
  • Review application logs, proxy logs, browser telemetry, and egress records around the exposure window for unexpected outbound requests from services or clients that used the SDK.
  • Check CI/CD and release artifacts for bundled copies of the compromised dist files, especially if frontend bundles or mobile builds included the SDK during the affected period.
  • Add dependency policy controls to block the specific malicious version and alert on unexpected scoped-package version bursts or dependency pins to compromised transitive packages.

Source notes

  • Socket reported the compromised version as @injectivelabs/sdk-ts@1.20.21 and identified fake telemetry used to exfiltrate wallet keys and mnemonics.
  • Socket reported that 17 additional @injectivelabs scoped packages at version 1.20.21 pinned or depended on the malicious SDK version.
  • Available source material says the malicious activity was detected and reverted quickly, but does not fully establish how the contributor account was accessed or whether all downstream artifacts were immediately removed.
